# Phase 12A: administrative access audit and internal notifications

## Reused boundaries and exact scope

Uses existing roles, Gate authorization, Branch access, ManageUser, permission
administration and Laravel's existing Notifiable trait/database notification
channel. No permission rows or approved role grants are added or changed. The
previous uncommitted Phase 11 approval-permission Seeder changes are preserved.

Existing financial, Captain status/employment, assignment and operational histories
remain authoritative and are not copied into this log. No generic administrative
access audit or database-notification inbox existed, so a narrowly scoped security
audit table and Laravel notification table are added rather than duplicating those
domain histories. No new financial or notification-provider dependency is installed.

## Administrative audit

ManageUser records creation, role/Branch assignment changes and active-status
changes. Role administration records permission grants/revocations and code
changes. Branch administration records creation, automatically granted creator
access, default-Currency configuration changes and activation/deactivation.
Before/after snapshots are taken under transaction/row locks; mutation and audit
commit together. Unchanged permitted values do not create duplicate records.
Core Role protection is rechecked after locking the Role before modification.

Only whitelisted values are stored: role/permission/Branch IDs, Role code,
active flags, Currency ID, and recipient/resource IDs for manual notices. Actor,
resource identity, appropriate Branch and microsecond timestamp are recorded.
Passwords, authentication/session tokens, user names/emails/phones and notice
title/body are not copied into audit payloads. Audit history is append-only in
the model and PostgreSQL, with restrictive actor/Branch FKs.

Audit viewing uses the existing manage-authorization Gate (SUPER_ADMIN only).
This intentionally prevents staff from viewing global User/Role access data or
cross-Branch history. SUPER_ADMIN retains its established all-Branch access.
Filters support actor, resource type/ID, action and Branch; results are query-based
and paginated. No new audit-view grants are inferred for employees or Captains.

Security-sensitive administration requires the new migration: if storage is not
activated, mutations roll back with an activation-required validation message.
Unchanged security values and ordinary profile edits do not create fake audits.
Historical migrations, financial contracts and already stored records are untouched.

## Internal notices

Active SUPER_ADMIN and ORDER_EMPLOYEE users have a private inbox, unread badge,
paginated list and idempotent mark-as-read action. CAPTAIN-only accounts have no
new access/write privileges. Mixed roles retain their explicitly assigned existing
staff role; Captain self-view authorization remains unchanged.

SUPER_ADMIN can explicitly send a manual plaintext notice to selected active
staff, maximum 50 per submission. Optional Branch context is validated for every
recipient. An optional Order link derives its Branch from the actual Order and
requires current orders.view plus Branch access for each recipient. No arbitrary
URLs or client-supplied route names are accepted.

Messages are stored through Laravel's database channel only, synchronously inside
the same transaction as one redacted NOTICE_SENT audit. Request UUID, canonical
payload hash, advisory lock and per-recipient uniqueness make exact retries reuse
the operation and reject conflicting reuse. Message text exists in the intended
recipient's notification payload, not in the audit. Sender is responsible for
appropriate plaintext content; no automatic business/private-data assembly occurs.

Inbox queries always use the authenticated User's notification relationship.
Counts, listing, read actions and link opening recheck current staff/Branch access;
Order-linked notices also disappear if Order permission or matching Branch is lost.
Safe links route through an ownership/authorization check and then the original
authorized Order workflow endpoint. Hidden notices contribute no visible count,
title, body or link. Existing notification types are not silently exposed.

No queue/broadcast/email/SMS/WhatsApp/push/API channel is enabled. No notices are
automatically generated by financial approval or operational transitions.

## Phase 12B: owner-approved automatic internal workflow notices

This section extends the earlier Phase 12A-only behavior above. Automatic bonus
and expense notifications are now explicitly approved; other suggested events
remain deferred. The existing manual-notice transport, recipient rules and audit
are preserved.

Connected actual CaptainBenefitReviewService transitions:
- SUBMIT: currently authorized reviewers for the specific bonus/expense permission.
- APPROVE / REJECT: the actual SUBMIT actor, rather than assuming draft creator.
- CANCEL: eligible reviewers only if the source was previously submitted/pending.
- Draft creation/revision, draft cancellation, REVERSE and general Order status
  transitions generate no automatic notices.

Approval eligibility is shared with the real approval service: active User,
captains.view, kind-specific approval permission and current access to the exact
request Branch. Creator, revision recorder and submitter are excluded even if
SUPER_ADMIN. Custom roles qualify by their actual permissions. The inbox's
read-only eligibility now supports users with existing captains.view, while each
workflow notice additionally requires its event-specific request authorization.
CAPTAIN default permissions and all financial/approval grants remain unchanged.
Manual notices still require current SUPER_ADMIN/ORDER_EMPLOYEE staff eligibility;
a custom reviewer cannot see old staff-only manual notices after staff-role removal.

A submission with no eligible reviewer stays PENDING and displays a warning. No
role/permission is granted and no recipient invented. Recipient IDs are captured
for the specific committed event; new grants do not retrospectively notify new
reviewers. Delivery rechecks current authorization, skipping revoked/inactive
recipients. Inbox counts/listing/read/open also reauthorize. Links use only the
existing protected captains.requests.show route. No evidence URLs, amounts,
names, descriptions, reasons, credentials or client-supplied destinations are stored.
Displayed wording is resolved in the current Arabic/English locale, distinguishing
approval from payout.

### Durable after-commit delivery and activation

The additive migration
2026_10_12_210249_create_captain_benefit_notification_events.php creates one small
delivery table: review_id primary key/FK, recipient_ids and delivered_at. This is
needed to survive a crash between business commit and notification insertion.
It is not a new financial source or entitlement table. Historical migration files
are untouched. No prior reviews are automatically backfilled.

The event is saved inside the existing lifecycle transaction. DB::afterCommit
creates database-channel notifications only after the outer transaction commits.
Rollback removes both review and delivery intent, and no callback is sent.
Delivery locks the event row and inserts deterministic event/recipient UUIDs via
Laravel Notifications; the notification primary key and event identity prevent
duplicate rows under retries/concurrent requests. Sending and delivered_at commit
together in a separate transaction. If sending fails, the underlying business
decision remains committed and the durable event remains pending, with an error
reported for retry. No notifications are automatically deleted.

abshir:deliver-benefit-notifications retries only pending recorded events, never
financial posting or lifecycle transitions. It is registered with the Laravel
scheduler every minute without overlap. Normal immediate delivery needs no queue;
crash recovery needs the normal Laravel scheduler running, or an explicit command
invocation. The command was executed only in isolated test schemas during this task.

Owner activation requires separate approval for the Phase 12A migration followed
by this Phase 12B migration. Neither was applied to owner databases. Before
delivery-schema activation the pre-existing Phase 11 lifecycle remains usable;
automatic notices require the new tables. No external channels/providers or new
dependencies are enabled.
